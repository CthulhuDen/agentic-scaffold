# agentic-scaffold

A portable AI-agentic workflow scaffold for software projects: an SPEC-driven governance layer,
subagent definitions for three harnesses (Claude Code, Codex, OpenCode), and the tooling that keeps
them in lockstep.

## Layout

| Path                          | Role                                                                  |
|-------------------------------|-----------------------------------------------------------------------|
| `AGENTS.md`                   | Project-root agent system prompt (stub; seeded once, project owns it) |
| `.agents/`                    | Conduct, implementer, and skill definitions shared by all harnesses   |
| `.claude/agents/`             | Canonical subagent prompts (Claude Code format)                       |
| `.codex/`, `.opencode/`       | Harness wiring; `agents/` is regenerated from `.claude/agents/`       |
| `policy/`                     | Governance rules                                                      |
| `tools/sync-agents.py`        | Regenerates Codex/OpenCode agent files from `.claude/agents/`         |
| `tools/scaffold.sh`           | Client-side wrapper for syncing with this scaffold                    |
| `tools/scaffold-sync.py`      | Bidirectional sync; runs on the scaffold side                         |
| `manifest.toml`               | File classification consumed by `scaffold-sync.py`                    |

## Prerequisites

- `uv` — `sync-agents.py` and `scaffold-sync.py` are uv-script invocations, and the SessionStart
  hooks for Codex and OpenCode call `sync-agents.py --check` on each session start.
- `bun` (only when using OpenCode) — needed to install the plugin's dependency in the consumer
  project. See the install step below.

## Installing into a project

From the scaffold repo:

```sh
uv run --cache-dir .tmp/uv-cache tools/scaffold-sync.py push /path/to/your-project
```

This writes managed files into the project, seeds stub files only if absent, installs the scaffold's
`.gitignore` block, and stamps `.agentic-scaffold-revision` with the scaffold's `HEAD` SHA. Then in
the project:

```sh
uv run --cache-dir .tmp/uv-cache tools/sync-agents.py
```

to materialize the Codex/OpenCode agent files. If OpenCode will be used, also install the plugin's
dependency once:

```sh
cd .opencode && bun add @opencode-ai/plugin@1.14.25
```

The plugin source is written against the 1.14.x API; consumers can drift to newer versions if the
API holds.

## Updating an existing project

From the project:

```sh
tools/scaffold.sh pull /path/to/agentic-scaffold
```

`scaffold.sh` cd's to the scaffold and invokes `scaffold-sync.py push <client>` there. Refuses if
either side has uncommitted changes in managed paths.

## Upstreaming local edits

From the project, after editing scaffold-canonical files in place:

```sh
tools/scaffold.sh push /path/to/agentic-scaffold
```

This invokes `scaffold-sync.py pull` in the scaffold. It reads the SHA recorded in the project's
`.agentic-scaffold-revision`, checks out an `incoming/<client>-<ts>` branch from that commit, copies
the project's managed files onto it, commits, and stamps `.agentic-scaffold-revision` on the client
side with the new incoming-branch commit. The maintainer reviews and merges that branch into the
default branch by hand, resolving conflicts with concurrent edits from other clients the normal way.

`.agentic-scaffold-revision` updates on both push (recording the scaffold's `HEAD`) and pull
(recording the new incoming-branch commit). The merge base for the next push from this client comes
from that recording, so concurrent edits from multiple clients diverge from a known common ancestor
and produce real 3-way merges rather than silent overwrites.

When the recorded revision is not an ancestor of the scaffold's current `HEAD` — typically because
the client pushed edits that the maintainer hasn't merged yet — pushing scaffold updates into the
client would overwrite the client's unmerged work. In that case the script warns and asks for
confirmation before proceeding.

## File classes

`manifest.toml` annotates each scaffold path:

- **managed** — overwritten on push, pulled back from a client on pull.
- **stub** — seeded on first push only (when absent in the client); never pulled. Used for
  project-owned files the scaffold seeds with a template (`AGENTS.md`, `policy/README.md`,
  `policy/verification-gates.md`).

A stub may declare `indexes = "<dir>/"`. When push adds new managed files under that directory,
the installer emits a notice to update the index by hand. (Pull never adds files, so no
notification is needed in that direction.)

## Canonical agent source

`.claude/agents/*.md` is the only editable source for subagent prompts. `.codex/agents/*.toml` and
`.opencode/agents/*.md` are regenerated by `tools/sync-agents.py` and carry an AUTO-GENERATED marker.
Edits to the generated files are caught by the SessionStart check and rejected.

## What the scaffold does *not* do

- **It does not push new files from a client to the scaffold.** Pull is bounded by the manifest; new
  files in clients are project-specific by definition. To upstream a new scaffold file, add it to the
  scaffold repo by hand, list it in `manifest.toml`, and the next push delivers it.
- **It does not auto-merge.** Pull from a client produces a branch the maintainer merges by hand.
- **It does not version itself.** Each project tracks the scaffold's HEAD SHA in `.agentic-scaffold-revision`;
  tagged releases are not part of the workflow.
